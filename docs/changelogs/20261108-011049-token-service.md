# Token service and the 7-day cap

- Adds `server/oauth/tokens.js` (plan Task 7.4): `issuePair(grantId)` issues an `xta_` access token (1 hour) and an `xtr_` refresh token (90 days), each 32 random bytes, base64url. Only SHA-256 hashes are stored. It also deletes up to 100 tokens that expired more than a day ago.
- `rotate(refreshToken, clientId)` spends the refresh token in one statement, so concurrent use lets only one request succeed. Reusing a spent refresh token revokes the whole grant. An unknown, expired, revoked-grant or wrong-client token returns `invalid_grant` without spending it.
- `resolveAccess(token, resource)` returns the user only for an unexpired access token whose grant is not revoked and whose resource matches the audience it was issued for.
- `server/session.js`: a bearer `xta_` token is checked against `<PUBLIC_APP_URL>/api`. An invalid one is a 401 and never falls back to the cookie. The `xt_` path is unchanged.
- Hand-made `xt_` tokens are capped at 7 days (plan D4): `expires_in_days` accepts 1 to 7 and defaults to 7. The token page offers 1, 3 and 7 days. The OpenAPI document, `docs/agents/api.md` and `public/llms.txt` say the same.
- Existing tokens are not changed here; that is plan Task 7.9.
- Tests: new `tests/api/oauth-tokens.test.js` (issuing, hashing, expiry, audience, rotation, reuse, wrong client, revoked grant, concurrency). `tests/api/tokens.test.js` gets cap tests, and its one 30-day fixture now uses 7 days.
