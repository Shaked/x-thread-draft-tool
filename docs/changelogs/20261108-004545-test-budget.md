# Test time budget (plan Task 4)

- `vitest.config.js` has two projects: `unit` (jsdom, the existing setup file, `tests/unit/**`) and `api` (node, `tests/api/**/*.test.js`, with a global setup).
- `tests/api/helpers/global-setup.js` applies the migrations once to a PGlite database and saves it as a compressed data dir under `node_modules/.cache/xt-test/`. The file name is a hash of `db/migrations/*.sql`, so a new migration rebuilds it. The path is passed to the API tests.
- `tests/api/helpers/db.js` loads that snapshot instead of replaying every migration. `migrate.test.js` still starts from an empty database, because it tests the migrations themselves.
- `scripts/test-budget.mjs` runs the whole suite, prints the five slowest files and the total, and exits 1 when a file takes more than 3000 ms or the run takes more than 30000 ms. The limits can be lowered with `TEST_BUDGET_FILE_MS` and `TEST_BUDGET_TOTAL_MS`. Script `npm run test:budget`; the CI unit job runs it instead of `test:unit`.
- Measured locally (16 files, 194 tests): total 6.9–7.2 s, down from about 14 s. Slowest file: `migrate.test.js` at about 2.3 s, under the 3 s stop-if line.
- `tests/api/migrate.test.js` is split in two: the re-run (idempotency) case moved to `tests/api/migrate-rerun.test.js`, each starting from an empty database, so no file is near 3 s.
